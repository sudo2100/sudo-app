## 1. 개요 (Overview)

### 1.1 배경
`sudo-soft2`는 React CSR(클라이언트 렌더링) + Express 서버 구조로 운영 중이다. 실제 운영하면서 다음 구조적 한계가 드러났다.

- **SEO**: CSR 특성상 최초 HTML이 빈 셸이라, 검색봇 대응을 위해 별도 헤드리스 브라우저 프리렌더링 스크립트(`scripts/prerender.cjs`, [plan/프리렌더링.md](프리렌더링.md))를 직접 만들어 붙여야 했다. 빌드 시점에 Chromium을 내려받아 렌더링하는 방식이라 빌드 시간이 늘고, 유지보수 부담이 있다.
- **가용성**: 무료 PaaS(Render)의 특성상 일정 시간 미사용 시 서버가 슬립 상태가 되어, 첫 요청에 수십 초 지연이 발생한다.
- **정적 콘텐츠 대비 과한 구조**: 홈페이지의 대부분(회사 소개/프로젝트 실적/Footer 등)은 자주 바뀌지 않는 정적 콘텐츠인데도, 매 요청마다 서버가 렌더링을 책임지는 구조로 되어 있다.

`sudo-soft3`는 같은 서비스(콘텐츠·기능 동일)를 **Next.js SSG(정적 생성) + ISR(증분 정적 재생성)** 구조로 재구축하고, 결과물을 **CDN(엣지 네트워크)** 을 통해 서빙하여 위 문제를 근본적으로 해결하는 것을 목표로 한다.

### 1.2 목적
- 정적 콘텐츠(회사 소개/프로젝트 실적/Footer 등)는 빌드 시점에 완전한 HTML로 생성해 별도 프리렌더링 도구 없이 SEO를 확보한다.
- 자주 갱신되는 콘텐츠(AI 뉴스)는 ISR로 주기적/온디맨드 재생성한다.
- CDN 엣지에서 정적 페이지를 서빙해 콜드스타트 없이 빠른 응답을 제공한다.
- `sudo-soft2`의 기능·데이터·운영 자산(도메인, DB, 상담 이력)을 최대한 승계한다.

### 1.3 타겟 사용자
`sudo-soft2`와 동일 (기업 담당자, 국비지원 교육기관, 개인 수강생, 해외/외국어 사용자). 사용자 관점에서는 겉보기 기능·화면이 동일해야 하며, 이번 프로젝트는 **아키텍처 전환**이 핵심이다.

### 1.4 성공 지표 (KPI)
| 지표 | sudo-soft2 대비 목표 |
|---|---|
| 최초 콘텐츠 표시 시간(FCP) | 프리렌더링/콜드스타트 지연 제거로 단축 |
| 검색봇이 읽는 최초 HTML의 본문 포함 여부 | 별도 스크립트 없이 항상 완전한 HTML |
| 빌드/배포 소요 시간 | Chromium 다운로드·렌더링 단계 제거로 단축 |
| 상담 신청 폼 제출 건수 | 기존과 동등 이상 유지 (기능 회귀 없음) |

### 1.5 범위 밖 (Out of Scope)
- 신규 기능 추가는 원칙적으로 제외 — `sudo-soft2`의 기능 패리티(feature parity) 확보가 최우선
- 콘텐츠/디자인의 대대적 변경 (마이그레이션 과정에서 불가피한 조정은 허용)

## 2. 아키텍처 결정 사항

### 2.1 렌더링 전략 (페이지별 매핑)
| 페이지/섹션 | 전략 | 이유 |
|---|---|---|
| `/`, `/en` (Hero/Profile/Projects/Footer) | **SSG** (빌드 타임 생성) | 콘텐츠가 자주 바뀌지 않음 |
| `/` 내 AI 뉴스 섹션 | **ISR** (`revalidate` 주기 재생성 + 온디맨드 재검증) | 주기적 갱신 필요, 매 요청 크롤링은 불필요 |
| `/admin` | **동적 렌더링** (SSR/`force-dynamic`) | 인증 필요, 개인정보 포함 → 정적 캐싱 대상에서 제외 |
| 상담 신청/로그인 등 쓰기 작업 | **Route Handler(API)** | CDN에 캐싱될 수 없는 동적 처리 |

> **주의**: "SSG/ISR + CDN"이 곧 "100% 정적 export(`next export`)"를 의미하지는 않는다. 상담 폼 제출, 관리자 인증처럼 서버 처리가 필요한 기능이 있으므로, **Next.js 하이브리드 렌더링(정적 페이지 + 서버리스 Route Handler)** 을 CDN 배포 플랫폼(예: Vercel) 위에서 운영하는 방식을 기본안으로 한다. 완전 정적 export가 필요하다면 상담/관리자 기능은 외부 백엔드(별도 API 서버)로 분리해야 하며, 이는 별도 의사결정이 필요하다.

> **범위 구분**: 본 프로젝트(`sudo-soft3`)는 **자기완결형** — 상담 폼·관리자를 같은 Next.js 앱의 Route Handler로 두고 Vercel에서 운영한다. 이는 향후 **사업용 제작 템플릿**(여러 고객사 사이트)과는 별개 트랙이다. 사업 템플릿에서는 폼 백엔드를 **공용 외부 API로 분리**해 다수 고객사가 공유하는 구조를 채택하며(국내 서버·데이터 국내 보관 등 요구 시 네이버 클라우드 등에 별도 배치), 그 결정은 이 문서 범위 밖이다.

### 2.2 배포 플랫폼
- **플랫폼 기본안: Vercel.** ISR·온디맨드 재검증·엣지 캐싱을 별도 설정 없이 네이티브로 지원한다.
- **정확한 근거**: ISR·온디맨드 재검증(`revalidatePath`/`revalidateTag`)은 Vercel 전용이 아니라 **Next.js 코어 기능이라 셀프호스팅(Render 등 Node 서버)에서도 동작**한다. Render 대비 실제 격차는 두 가지다 — ① 전 세계 **엣지 CDN 분산**을 기본 제공하지 않음, ② 다중 인스턴스·재배포 시 **ISR 캐시 정합**을 위해 공유 캐시 핸들러(예: Redis)를 직접 붙여야 함. 여기에 무료 플랜 콜드스타트가 더해져, Render는 이번 SSG/ISR 전환 목적과 결이 맞지 않는다.
- **리전 전략**: 방문자가 받는 **정적/ISR 페이지는 엣지 CDN(서울·도쿄 POP 포함)에서 서빙**한다. 미국 왕복 소지가 있는 **동적 함수(상담 POST·관리자·뉴스 재생성)는 함수 리전을 서울(`icn1`)로 지정**한다(플랜별 가용 여부는 착수 시 확인).
- **대안 플랫폼 등급**: Netlify = Next.js 지원이 Vercel에 근접(1순위 대안). Cloudflare Pages = 한국 엣지·비용은 매력적이나 Next.js(ISR·Node 런타임) 운영에 `@cloudflare/next-on-pages` 어댑터·엣지 런타임 제약이 있어 **호환성 검증 후 채택**.
- 커스텀 도메인은 `sudo-soft2`에서 쓰던 도메인(`sudo-app.kr`)을 승계하는 것을 전제로 하되, 전환 시점의 DNS 절체 계획을 별도로 수립한다.

## 3. 정보 구조 (Site Map)

```
/                (기본 언어, SSG + 부분 ISR)
/en              (영문, SSG + 부분 ISR)
/admin           (관리자 대시보드, 동적/인증 필요)
/api/ai-news     (Route Handler, GET)
/api/contact     (Route Handler, POST)
/api/contacts    (Route Handler, GET, 관리자 인증)
/api/admin/*     (Route Handler — login/logout/me/stats)
/api/revalidate  (Route Handler, POST — 온디맨드 ISR 재검증 트리거, 시크릿 토큰 보호)
```

i18n은 `sudo-soft2`처럼 클라이언트 상태로 전환하는 방식 대신, **Next.js 라우팅 기반(정적 생성 가능한 `/`, `/en` 경로 분리)** 을 우선 검토한다 — 언어별로 완전한 정적 HTML을 빌드해야 SEO 이점을 최대화할 수 있기 때문이다.

## 4. 기능 요구사항 (Functional Requirements)

기능 요구사항은 원칙적으로 `sudo-soft2`와 동일하며, 렌더링/데이터 취득 방식만 아래와 같이 바뀐다.

### 4.1 정적 섹션 (Navigation/Hero/Profile/Projects/Footer/일정 안내 팝업)
- 빌드 타임에 콘텐츠가 확정되는 SSG 페이지로 구현한다.
- 콘텐츠 변경 시 재배포(재빌드)가 필요하다는 점을 콘텐츠 관리 주체에게 명확히 안내한다.

### 4.2 AI 뉴스 피드
- 데이터 수집은 서버(Route Handler 또는 Vercel Cron)에서 주기적으로 수행한다.
- 페이지는 ISR로 일정 주기(예: 1일 1회, `sudo-soft2`의 오전 7시 갱신 정책 승계 검토) 재생성한다.
- 긴급 갱신이 필요할 경우를 대비해 `/api/revalidate` 온디맨드 재검증 엔드포인트를 둔다.
- 뉴스 데이터를 가져오지 못하는 경우의 폴백 UI(로딩/에러/빈 상태)를 유지한다.

### 4.3 코칭/자문 상담 신청 (ContactForm)
- 폼 자체는 클라이언트 컴포넌트로 유지하고, 제출은 Route Handler(`/api/contact`)로 처리한다.
- DB 저장 + SMTP 이메일 알림 로직은 `sudo-soft2`와 동일하게 승계한다.
- 정적 페이지 내에 포함되지만, 제출 동작 자체는 캐싱되지 않는 동적 요청임을 보장한다.

### 4.4 다국어 지원 (i18n)
- 한국어(`/`)/영어(`/en`) 각각 완전한 정적 페이지로 생성한다.
- 언어 전환 UI 클릭 시 해당 로케일 경로로 이동한다.
- AI 뉴스 원문은 번역 대상에서 제외한다 (기존과 동일).

### 4.5 관리자 페이지 (/admin)
- 인증되지 않은 사용자에게 상담 신청자 개인정보가 노출되지 않아야 한다 (필수 요구사항, `sudo-soft2`에서도 최우선 원칙이었음).
- 세션 기반 인증(로그인 → 서명된 세션 쿠키)을 유지한다.
- 통계(총 접수/오늘 접수/최근 7일/코스별 분포) 및 접수 내역 표를 제공한다.
- 이 페이지는 정적 캐싱 대상에서 명시적으로 제외한다.

### 4.6 AI 챗봇 (선택 기능)
- 필요 시 Route Handler로 구현하고, 프론트 노출 여부는 `sudo-soft2`와 동일하게 별도 검토 사항으로 둔다.

## 5. 데이터 마이그레이션

- `contacts` 테이블 스키마는 `sudo-soft2`와 동일하게 유지해 **기존 PostgreSQL(Neon) 인스턴스를 그대로 재사용**한다 (데이터 이관 불필요, 연결 문자열만 재사용).
- 환경변수 체계(`POSTGRES_URL`, `EMAIL_USER`/`EMAIL_PASS`, `ADMIN_USERNAME`/`ADMIN_PASSWORD`, `ADMIN_SESSION_SECRET`)를 승계한다.
- `GEMINI_API_KEY` 등 AI 챗봇 관련 환경변수도 필요 시 승계한다.

## 6. 비기능 요구사항 (Non-Functional Requirements)

| 구분 | 요구사항 |
|---|---|
| SEO | 별도 프리렌더링 도구 없이, 빌드 결과물 자체가 완전한 정적 HTML이어야 한다 |
| 성능 | 정적/ISR 페이지는 CDN 엣지(서울·도쿄 POP)에서 응답해 콜드스타트 지연이 없어야 한다. 동적 함수(상담·관리자·재검증)는 함수 리전을 서울(`icn1`)로 지정해 국내 지연을 최소화한다 |
| 캐시 정합성 | ISR 재생성 주기와 온디맨드 재검증 시점을 명확히 정의해, 오래된 뉴스가 과도하게 오래 노출되지 않도록 한다 |
| 보안 | `/admin`, `/api/contacts`, `/api/admin/*`는 인증 없이 접근 불가해야 하며, 이 요구사항은 캐싱 전략과 무관하게 항상 성립해야 한다 |
| 반응형/접근성 | `sudo-soft2` 기준 유지 |
| 관측성 | ISR 재생성 실패, AI 뉴스 수집 실패 시 로그로 확인 가능해야 한다 |

## 9. 개발 진행 방식 (마이그레이션 단계 제안)

1. **정적 페이지 이관**: Hero/Profile/Projects/Footer를 Next.js SSG 페이지로 재구현 (콘텐츠는 `sudo-soft2` 그대로 이식)
2. **i18n 라우팅 설계**: `/`, `/en` 정적 생성 구조로 전환
3. **AI 뉴스 ISR 적용**: 수집 로직 이식 + ISR/온디맨드 재검증 연결
4. **상담 폼 Route Handler 이관**: DB/이메일 연동 이식 + 캐싱 제외 검증
5. **관리자 페이지 이관**: 인증/세션/통계 로직 이식, 동적 렌더링 강제 설정
6. **배포 전환**: 신규 플랫폼(Vercel 등) 연결 → 스테이징 검증 → 도메인 절체
7. **레거시 정리**: `sudo-soft2`의 Express 서버, 프리렌더링 스크립트(`scripts/prerender.cjs`) 등 더 이상 불필요한 구성 요소 식별 및 정리 계획 수립

## 10. 리스크 및 오픈 이슈

| 항목 | 내용 |
|---|---|
| 완전 정적 export 불가 | 인증/DB 쓰기 작업이 있는 한 `next export` 순수 정적 방식은 채택 불가 — 하이브리드(SSG+ISR+서버리스) 구조임을 이해관계자에게 명확히 전달 필요 |
| i18n 라우팅 전환 비용 | 클라이언트 상태 기반(`localStorage`) → 라우팅 기반으로 바꾸면 컴포넌트 구조 변경이 필요 — 마이그레이션 범위/일정에 반영 |
| ISR 재생성 주기 확정 | AI 뉴스의 "최신성"과 "빌드/재생성 비용" 사이 트레이드오프를 확정해야 함 (예: 1일 1회 vs 온디맨드 위주) |
| 도메인 절체 계획 | 기존 `sudo-app.kr` 도메인을 다운타임 없이 신규 플랫폼으로 옮기는 절차 별도 수립 필요 |
| 배포 플랫폼 종속성 (락인) | 종속 정도는 **중간**. 진짜 종속은 코드가 아니라 "엣지/ISR 인프라 편의"다. **완화책**: 코드를 표준 Next.js 범위(ISR·Route Handler·Cron 코어 기능)로 유지하면 Netlify 등으로의 이전이 대체로 설정 수준에 그친다. Vercel 전용 API·프리미티브 남용을 피한다 |
| Cron 타임존 | Vercel Cron은 **UTC 기준**이다. AI 뉴스 "오전 7시(KST) 갱신"은 **22:00 UTC(전날)** 로 환산해 설정한다 |
| 함수 리전 미지정 | 함수 리전을 명시하지 않으면 기본(미국 등) 리전에서 실행돼 국내 동적 요청 지연이 커질 수 있다 — `icn1`(서울) 지정을 착수 체크리스트에 포함 |
